# Drawing the architecture

The diagrams of this project are **draw.io files** drawn with the official Azure icons. The `.drawio`
is the source; the PNG is an export of it. Nothing here is generated from Python any more: open the
file in draw.io, change it, export it.

| Diagram | Source | Export |
|---|---|---|
| One-picture overview, for sharing | `docs/images/azure-architecture-overview.drawio` | `.png` next to it |
| Detailed architecture | `docs/images/azure-architecture-detailed.drawio` | `.png` next to it |

The older `azure-architecture-layered`, `azure-architecture` and `azure-architecture-post` images are
still generated by the scripts in `tools/diagrams/`; replace them with draw.io files when they next
change.

## The workflow

1. Edit the `.drawio` (draw.io desktop, or app.diagrams.net with the file open).
2. `python tools/diagrams/check_drawio.py docs/images/<name>.drawio` until it reports no errors.
3. Export: draw.io `File > Export as > PNG`, 200 % scale, or
   `node tools/diagrams/render_drawio.mjs in.drawio out.png` (Playwright from `apps/web`; it uses
   draw.io's own viewer).
4. **Look at the picture**, zoomed in on every region. A check cannot see a label sitting on an arrow.
5. Check every label against the code (next section), then update the README and
   `docs/AZURE-ARCHITECTURE.md` if the picture changed what they say.

In a Claude Code session the check runs by itself after every write to a `.drawio` file
(`.claude/settings.json`), and the project skill `drawio-diagrams` carries these rules.

## Accuracy: the diagram must match the project

A diagram that is clear but wrong is worse than none. Trace each box to a source before drawing it:

| Draw | Look at |
|---|---|
| Azure resources, how they connect | `infra/terraform/modules/nodo/*.tf` (the resource, not the README) |
| Scaling (`min` to `max` replicas) | `local.api_scale`, `local.web_scale`, `voice_scale`, the job `event_trigger_config` |
| Recovery targets | the comment at the top of `dr.tf` (RTO 30 to 60 minutes; RPO seconds for the database, minutes for audio) |
| What the application does | `services/api/src/nodo_api/`, `docs/adr/` |
| Optional parts | the variable that switches them (`voice_enabled`, off by default) |

Things this project already got wrong once, so check them first:

- The worker is a **Container Apps job**, not an app.
- The web interface and the API are **two** Container Apps.
- The REST gateway and the **AI gateway are one** API Management instance.
- The audio storage is reached by the browser through **short-lived signed upload links**: do not call
  the data tier "private only".
- The voice session store is **Azure Cache for Redis** (`azurerm_redis_cache`), not Managed Redis.
- Scaling labels describe the professional tier; say so in the legend.

**No status wording in a diagram.** Never write "not deployed", "without a subscription", "target" or
similar: what has and has not been run belongs in the README and `AZURE-ARCHITECTURE.md`, which this
repository keeps honest. A diagram shows the design. The checker refuses these phrases.

## What a clear diagram looks like

- **Order of the page**: public edge and identity, then the private network (with its lanes), then
  the standby region, then observability, security and delivery.
- **Trust boundary**: one red dashed line between the public edge and the private network, labelled.
  The arrow from Front Door crosses it.
- **Lanes**: a lane is one path (REST and batch, live voice). Put an optional path in a dashed box
  and say "optional add-on, off by default" in its title.
- **Legend**: solid line, dashed line, dashed box, trust boundary. Required whenever something is dashed.
- **Scaling and resilience on the box**: `API · 3–N replicas`, `Voice gateway · 2–N replicas`,
  `Worker · KEDA on queue depth`, `0→N replicas on failover`, `zone-redundant HA`,
  `RTO 30–60 min`, `RPO seconds (database), minutes (audio)`.
- **One idea per arrow**, labelled with what travels (`WSS`, `jobs`, `finished transcript`). Name the
  protocol on the arrow that crosses a boundary. One double-headed arrow for a two-way exchange.
- **At most about 25 icons** on a page; split into overview and detail rather than shrinking text.

## Drawing rules (what the checker enforces)

- Icons are the official `img/lib/azure2/...` stickers, 72 px, always with a label (bold name, grey
  detail line of at most five words). The icon names that exist and are used here:
  `networking/Front_Doors`, `app_services/API_Management_Services`, `identity/External_Identities`,
  `identity/Users`, `other/Container_App_Environments`, `other/Worker_Container_App`,
  `integration/Service_Bus`, `ai_machine_learning/Azure_OpenAI`, `ai_machine_learning/Speech_Services`,
  `app_services/Search_Services`, `databases/Azure_Database_PostgreSQL_Server`, `databases/Cache_Redis`,
  `storage/Storage_Accounts`, `security/Key_Vaults`, `security/Azure_Defender`,
  `networking/Private_Endpoint`, `devops/Application_Insights`, `analytics/Log_Analytics_Workspaces`,
  `management_governance/Alerts`, `management_governance/Policy`, `general/Workflow`.
  A name that does not exist draws nothing: open it in draw.io or fetch
  `https://app.diagrams.net/img/lib/azure2/<name>.svg` to confirm.
- Icons do not overlap and sit at least 20 px inside the group that holds them.
- No text below 12 px. Titles 28 px or more.
- Arrows are orthogonal, 3 px, with a block head; they never run through an icon. Where a straight
  line would cross something, give the arrow waypoints and route it through the free gap. In a row of
  icons put the labels on the same side (above or below) so the other side stays free for arrows.
- Every arrow has a source and a target. Labels on arrows have a white background.
- Light background, one blue for flows and a handful of neutral tints for groups. Colour never carries
  meaning alone: dashed is optional, red dashed is the boundary.
- English, sentence case.
- Never the words Claude or Anthropic.

## Exporting for LinkedIn or a README

Use the overview (1800 × 1110 page, 3600 × 2220 PNG) for a feed post: it stays legible on a phone.
The detailed view is for the README and the architecture document.
